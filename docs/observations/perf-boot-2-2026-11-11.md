# Faster boot, part 2: outline rays, curb grids and tram/rail nearest queries (2026-11-11)

## Question

Part 1 ([record](perf-boot-predicates-2026-11-11.md)) indexed the load-time point-in-polygon predicates and took the
boot from 18.4 to 11.9 s at 1× CPU. Its profile left `outlineRay` (14–17 % self, `js/buildings.js`), the
`tram-infra.js` `nearest`/`poleAt` queries, the `street-details.js` `distPointToSeg`/`nearestCurbFrame` work and
`road-network.js` `crossingRuns` at the top. This round indexes the geometry those functions scan, with the same rule
as part 1: the index only chooses which edges/segments the unchanged arithmetic sees, so every build output stays
bit-identical. No `js/geodata.js`, world data or drawn geometry changed.

## What changed

- **Block outline rays (`js/buildings.js`).** The frontage rule samples every lot side of a block against the block's
  curb outline: the 2026-11-11 headless block build made 218 k `outlineRay` queries over 21,724 lot rects and only 6 %
  of them crossed within `FRONT_RAY` (18 m). Each block's outline edges are now filed once in a CSR grid (about 256
  cells, 4–16 m; `Int32Array` offsets and edge ids) and the ray visits only the cells its 18 m segment touches. The
  exact intersection formula is unchanged; a crossing farther than `FRONT_RAY` returns `Infinity` (the caller ignored
  every such value already). The grid is dropped when the build reaches the next block and again at the end.
- **Reserve lists (`buildings.js`).** `minusReserves` was rebuilding the 38 landmark reserves in the current frontage
  frame, and the block's anchor/object boxes, for every one of its 13,233 calls. The list is now cached on the block
  and the arrays that define it (`srcBlock`, `xf`, `srcAnchors`, `srcObjectReserves`) and dropped at the end.
- **Bridge corridors (`buildings.js`).** `hitsBridgeCorridor` ran the full four-axis separating-axis test for 51,899
  calls against 85 corridor boxes (4.4 M full tests, no lot ever touched a deck). Each corridor now carries its world
  AABB (1 µm of grace) and the exact test runs only for corridors whose AABB meets the rect's. Both boxes are
  conservative, so the boolean is unchanged.
- **Curb edges (`js/street-details.js`).** `blockCurbDist` and `nearestCurbFrame` ask a block's curb outline again and
  again (24.5 k lamp checks and 32.7 k mapped trees in the same build; up to 478 queries on one block). Each block's
  edges are filed in a 4 m grid for this build only. `blockCurbDist` now takes the clearance it is compared against and
  returns the first edge closer than it (or `Infinity`), because every call site only tests `< reqDist`/`>= reqDist`;
  `nearestCurbFrame` expands rings until the ring's lower bound passes the best distance, keeping the first edge of an
  equal distance and computing the frame once for the winner. The 8 m grid margin covers points on the sidewalk outside
  the curb bbox; a point farther out falls back to the full scan. In a separate headless street-details run the lamp
  section fell from 716 to 346 ms and the mapped-tree section from 1,759 to 780 ms (its whole 5.7 → 4.1 s build
  includes the road network, which this pass did not change).
- **Tram/rail segment grids (`js/tram-infra.js`).** `segmentGrid.nearest` now rejects a segment by its bbox grown by the
  best distance found so far before doing the segment arithmetic. In the tram layout that cut the lane grid from 8.16 M
  candidate tests to 0.64 M for 215 k queries (38 per query). `poleAt` buckets poles in 4 m cells and returns the
  lowest-index match, which is the pole the old linear scan over 4,490 poles found first.
- **Rail deck / viaduct tests (`tram-infra.js`).** `underDeck` asks the deck grid 645 k times in the rail layout, almost
  always far from any deck: it now rejects points more than 25 m outside the decks' union box and memoises the last
  point (`roadDist` and `tramDist` ask it twice for the same point). The deck grid moved from 32 to 128 m cells (a
  25 m query then needs one or two Map lookups, not four to nine), and each viaduct's end box is tested before its two
  ramp-distance hypots (99 viaducts × 13,609 pieces).

The one-slot block index in `buildings.js` and the per-block curb grid in `street-details.js` are transient; all maps
and typed arrays are dropped when the build returns, so the retained boot index memory above part 1's block indexes is
zero. The `segmentGrid` bbox fields add four numbers per filed segment while the layout runs (the lane grid's ~190 k
segments), then go with the grid.

## Equivalence evidence

- **Build hashes.** `git archive a299cdd` vs this tree, both through the test `loadModule` harness, 45 hashes
  identical: buildings colliders / `footprintsByBlock` / `allBlocks`, city-grid colliders / prop colliders /
  footprints / sidewalks / 61,550 tree sites / 3,511 lamps / cut and road-cut plaza slabs, street-details footprints /
  colliders / audio signals / tree placement / its road network (node and edge rows), the traffic network and
  crosswalks, all 10 tram layout fields and 12 rail layout fields, the full road-paint strip arrays and the P-22 bus
  marks, plus the four `[cityGrid]`/`[streetDetails]`/`[road-network]` console summaries.
- **Traffic.** `node tools/bench-traffic.mjs --only centrum --seed 4242 --json <file>`: the JSON is byte-identical
  before and after (724 bytes; the human report's header prints its own wall time, which is not part of the JSON).
- **Predicates:** the new `tests/boot-indexes.test.cjs` compares every index with its plain scan: the block outline
  rays on every sampled vertex/edge/±1 µm in 8 directions (the plain value ≤ 18 must be bit-equal; farther must be
  `Infinity`), distances, a synthetic 500 m outline whose vertices sit on cell lines, the bridge SAT on every real
  corridor and 25,000 random rects in three frames, the segment grid on 30,000 queries against the same grid with the
  bbox reject disabled, the pole lookup against the linear scan, and the curb frame/reach on real and synthetic
  outlines.
- **Regression test:** `tests/boot-indexes.test.cjs` (6 tests, ~4 s). `node --test tests/*.cjs` passes (505 tests) and
  `node --test tests/` passes (521 tests), both after the final edits.

## Limits

- The browser pairs ran on a machine with other agents' builds (load average 7–53); the absolute times are inflated
  and vary by tens of percent. The 1× pairs were repeated in both orders and agree on the direction: blocks −31 to
  −36 %, traffic −2 to −19 %, total −6 to −16 %. The 6× pairs move within a few percent and their phase splits follow
  the machine state (the `compile`/`warmup` rows differ by up to 14 % even though neither tree changed them).
  A phone-level 6× throttle is a JS slowdown, not a device.
- The CPU profile's sample stream is bursty (in a headless run `pavedPlazas` collected 10.5 k samples in 178 ms),
  so function shares were used only to find candidates; the phase timings and the wall times are the reported result.
  `nearestCurbFrame` in particular is attributed 0.5–0.6 % of the baseline boot and 3–5 % of this one, while the
  wall-clock tree section it serves fell from 1,759 to 780 ms: the sampler over-weights its tight ring loop. The
  profile table below therefore lists only functions whose direction the wall times confirm.
- The equivalence hashes cover the headless build (the same production modules with inert three.js/TSL); they do not
  render. The changes do not touch materials, shaders or scene graph construction, but a browser check of the city is
  still the final appearance test.
