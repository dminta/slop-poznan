# Faster boot, part 4: curb-ring traversal, corner-link bands and outline distances (2026-11-12)

## Result

On the current `1854272` baseline, median precompile `[init]` time falls **7.159 → 6.696 s at 1× (−6.5%)** and
**45.424 → 42.744 s at 6× (−5.9%)**. Total `[init]` through the first frame and GPU completion falls
8.551 → 8.138 s / 55.314 → 53.426 s. These are three runs per configuration, headless desktop WebGPU; they are not
phone measurements. The output hashes remain identical and retained memory does not grow.

## Method

Read the previous [predicate](perf-boot-predicates-2026-11-11.md), [part 2](perf-boot-2-2026-11-11.md) and
[part 3](perf-boot-3-2026-11-11.md) records first. Their `.agent-task` scripts were absent in this worktree, so this
pass rebuilt the harnesses instead of treating old absolute timings as the baseline.

- Serve this worktree with `python3 -m http.server 8194`, not port 8000. Extract `git archive HEAD` into
  `.agent-task/base` before editing; all baseline source comes from that extraction. No other checkout is used.
- Chrome 157 / Apple M5 Pro, `--headless=new --enable-unsafe-webgpu --enable-precise-memory-info
  --js-flags=--expose-gc`, a separate `/tmp/boot4-chrome` profile, CDP port 9394, 1280 × 720, DPR 1.
- `.agent-task/perf/browser.mjs` loads the **production entry unchanged**, with `?quality=high&stats=1`, captures the
  actual `[init]` console line, a 200 µs CDP CPU profile from navigation through that line, and GC/heap usage. It
  records exceptions and console warnings/errors. CPU throttle is applied before navigation. Baseline 1×/6× runs
  alternate, then final 1×/6× runs alternate; this is repeated sampling, not randomized A/B. The third baseline 6×
  run was repeated explicitly against the archive to exclude a possible edit/loading overlap.
- The main result excludes `compile`, `warmup`, `firstFrame` and `gpu` from the phase sum. Module evaluation before
  `initApp`, including the land raster, is outside that sum but inside the navigation CPU profile and `loadMs`.
  Total `[init]` includes shader/warm-up/GPU phases. Wall phases include waits and GC; sampled self/inclusive CPU
  estimates should not be added to them.
- `.agent-task/perf/node.mjs` uses `tests/helpers/module.cjs` and the benchmark's inert Three.js/TSL stand-ins,
  builds blocks → cityGrid → streetDetails → traffic → tram/rail layouts → signal heads → paint → infrastructure,
  and passes the grid's populated live exports explicitly. Like the earlier headless records it omits building,
  landmark and bridge colliders. It uses the real species crown radii. Unlike the earlier phase table it also times
  `addRuntimeSignalHeads`, whose materialisation of lazy pedestrian links is a substantial part of browser traffic.
  Capturing tree sites and paint arrays adds identical hashing overhead inside those two phases. All other hashes
  are outside the timed phase. Three final interleaved baseline/current pairs were run; one pair also has Node CPU
  profiles. Initial exploratory runs with incomplete stubs are excluded from the final Node table.
- Raw JSON, CPU profiles, screenshots, scripts and the full test log remain under `.agent-task/perf/`. Run
  `node .agent-task/perf/aggregate.mjs` to rebuild the browser medians and profile table. Scratch instrumentation is
  confined to `.agent-task`; production has no timing hooks or globals added.

The decisions from that profile:

- **Curb search: excess loop iterations.** The grid already reduced 25,434 mapped-tree queries to 95,052 exact edge
  tests in the headless fixture. However, each expanding ring iterated a whole square and skipped its interior.
  Counters measured **195,020,155 loop visits for 275,053 rings**. The work was traversal, not a missing index.
- **Outline distance: missing nearest-distance hierarchy.** The earlier ray grid has a short reach; a distance query
  can stand far inside a large block. The old full scan still spent 1.63 s self at 6×. A hierarchy can prune distant
  edges without changing the nearest-distance arithmetic or the frontage setbacks that read the exact result.
- **Corner links: computing a result never read.** The Node profile put `cornerClear` first (2.87 s self / 3.11 s
  inclusive), and the browser confirmed ~0.99 s self at 6×. Its caller only needs every one-metre sample within the
  4 m band; the exact minimum over all edges is unused.
- **Polygon tests / block lookup:** already indexed; the cost is repeated exact queries and edge arithmetic.
  No new cache was added because block priority and boundary ties matter, and this pass found larger, simpler wins.
- **Road/rail clearance:** already spatially bucketed. Their projection and `Math.hypot` work remains prominent.
  Replacing `hypot` with a square root is not a bit-identical transformation; it was not applied. Further work should
  count candidates/callers and find conservative rejects or exactly repeated inputs first.
- **Signal-head audit:** despite its name it is live placement work. `addRuntimeSignalHeads` calls it with `place=true`;
  its output creates poles, arms and heads. Removing it as a logging-only audit would change the scene. Its curve,
  lane and building indexes also support actual placement. No log-only whole pass was removed.

## Changes and individual measurements

1. **`street-details.js`: visit each ring's perimeter directly.** Interior columns visit just their top/bottom cells;
   outer columns visit the side. Clip x to the grid, keep the old z bounds, stamp, lower-distance stop and first-edge
   tie rule. Counters fall to **19,124,802 loop visits**, with exactly the same 275,053 rings and 95,052 edge tests.
   No new storage is allocated or retained.
2. **`pedestrian-routes.js`: stop the edge scan once distance ≤ 4 m.** Preserve the obstacle/block check, one-metre
   samples, endpoint pairing, projection, `hypot`, `Math.min` and inclusive threshold. Later finite edges can only
   reduce that minimum. This also reduces runtime lazy-link work; the routes themselves are unchanged.
3. **`buildings.js`: nearest-distance hierarchy.** Lazily add a binary hierarchy to the existing single-block outline
   cache. Split edge-centre order on the longer axis; leaves hold at most eight edge ids. A reusable typed stack
   visits the nearer child first, rejects only by outward-expanded bounds (0.1 µm slack), and evaluates the original
   squared-distance expression on surviving edges. The final `Math.sqrt(best)` and every frontage setback remain
   exact. Replacing the source block replaces the whole cache; the existing `outlineIndex = null` drops the final
   hierarchy after the block pass. There is no all-block distance cache.

Exploratory checkpoints, each after one change, milliseconds. These single runs locate the gain; the three-run
medians below carry the final result. The Node checkpoints used the same earlier exploratory harness, without the
final tree/paint hash extensions, so they compare only with each other.

## Trials, rejections and limits

- A smaller four-edge hierarchy leaf was rejected in a headless probe sweep over 80 interior/exterior points per
  block: **370 ms versus 312 ms** with eight-edge leaves, with equal distance sums. Sixteen/thirty-two leaves took
  271/248 ms in that artificial sweep; they were not adopted from a VM microbenchmark because the real browser and
  actual frontage-query distribution choose the result. Eight leaves is measured in the browser tables, not claimed
  as an exhaustive tuning optimum.
- A whole-city lazy-route hash attempted to call `next` on every sidewalk. It ran beyond two minutes and was stopped;
  that would measure materialising routes the browser boot never asks for. The final harness instead records the
  actual `links` results generated during signal placement, and the regression test compares the changed predicate
  against its full-scan reference directly. That exploratory run is excluded from all phase/profile numbers.
- No `hypot`/sqrt substitutions, coordinate quantisation or placement arithmetic rewrites were applied. No workers,
  deferred first-frame work, shader changes, geodata changes or three.js SHA bump were needed.
- Browser runs share a machine with other work. Baseline/final batches are not randomized paired trials; unchanged
  phases drift and the exact percentage is uncertain. CPU throttle is a JS slowdown, not a phone or thermal model.
  Screenshot/smoke and full-suite work started only after the repeated boot measurements.
- The remaining top three helpers cost about **5.65 s self at 6×** together. Even deleting all that work would leave
  roughly 37 s of the precompile init budget. Any much larger improvement now needs a broader representation or
  scheduling change justified by a real-device profile; workers/deferral and geodata-format changes remain outside
  this code change.

### Memory

High-tier retained JS memory after forced GC (`usedSize + backingStorageSize`) has median **843.50 → 843.45 MiB**
at 1× across the three baseline/final runs. At 6× it is 842.09 → 842.91 MiB, inside the 841.66–844.06 MiB range
of these samples. The typed-array/backing storage stays ~348.15 MiB. After three minutes of ordinary high-tier
simulation it is 845.69 MiB; after one minute on low it is 783.34 MiB, including newly materialised runtime routes.
The hierarchy's only owner is the existing cleared `outlineIndex`; the other changes add no retained structures.
This is GC/heap-usage measurement plus an ownership check, not another retained-object heap-snapshot audit.
